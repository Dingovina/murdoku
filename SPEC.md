# Murdoku — спецификация игры

Детективная вариация судоку-подобных пазлов (в духе LinkedIn Queens). На поле из комнат
расставляются люди (подозреваемые + убитый); набор подсказок однозначно определяет позиции
всех людей, а игрок должен вычислить убийцу.

Статус: спецификация зафиксирована. Реализация — отдельные этапы (см. план).
Отложено в v2: составные портреты, рандомные имена, сохранение игр в БД, меню уровней.

---

## 1. Поле

- Поле описывается габаритным прямоугольником `W × H` клеток. Координаты `(r, c)`,
  `r = 0` — верхняя строка, `c = 0` — левый столбец.
- **Игровое поле** — подмножество клеток прямоугольника: 0–2 комнаты могут быть
  **исключены** из поля. Исключённые клетки («пустоты») не принадлежат ни одной комнате,
  не могут содержать объекты и людей и **не фигурируют в подсказках**. Пустоты дают
  силуэтам поля разнообразие вместо строгого прямоугольника. Суммарная площадь пустот —
  не более 30% площади прямоугольника.
- Между некоторыми парами ортогонально-соседних клеток игрового поля стоят **стены**.
  **Комната** — максимальное связное (по ортогональной смежности без стен) множество
  клеток игрового поля; пустоты и габаритная рамка — стены.
- Каждая клетка игрового поля принадлежит ровно одной комнате. Комнаты — произвольные
  полиомино.
- В данных пазла перечисляются только реальные комнаты (списками клеток); клетки, не
  покрытые ни одной комнатой, — пустоты.
- «Угловая» клетка комнаты — клетка комнаты с минимальной парой `(r, c)` в
  лексикографическом порядке. Комнаты нумеруются `Комната_1 … Комната_R` сортировкой
  по угловой клетке (сортировка детерминирована).

## 2. Объекты

- Объект-экземпляр — связное (по ортогональной смежности) множество из 1+ клеток,
  **все клетки в одной комнате**; объект принадлежит этой комнате. В одной клетке
  не более одного объекта.
- Каждый экземпляр имеет уникальный `id`, но **тип может повторяться** в пазле
  (два стола — допустимо).
- Два класса типов:
  - **Полные** — человек не может стоять на клетке объекта:
    `стол`, `телевизор`, `шкаф`, `холодильник`.
  - **Частичные** — человек может стоять на клетке объекта:
    `кровать`, `ковёр`, `кресло`, `диван`.
- Многоклеточность:
  - `кровать` — **всегда ровно 2** ортогонально-соседние клетки одной комнаты
    (частичный: стоять можно на любой из двух клеток).
  - Остальные типы генерируются одноклеточными экземплярами.
  - **Слияние — UI-фича**: соседние экземпляры **сливаемого** типа в одной комнате
    отображаются как один крупный объект. Сливаемые типы: `стол`, `ковёр`;
    остальные (включая `кровать`) — не сливаются. На солвер, генерацию и семантику
    подсказок слияние **не влияет** (семантика экзистенциальна по клеткам, см. §4).
- Реестр типов — константа:
  `{тип → класс (полный/частичный), иконка, размер (1 | ровно 2), слияние (да/нет)}`:
  слияние включено у `стол` и `ковёр`, у остальных выключено. Легко расширяется.

## 3. Люди

- Всего `N` людей, `N ≥ 3`: один **убитый** (игрок знает, кто) и `N − 1` **подозреваемых**
  (`Подозреваемый_1 … Подозреваемый_{N−1}`). Ровно один подозреваемый — **убийца**.
- Идентификаторы: подозреваемые — `suspect_1 … suspect_{N−1}` (номер = число в имени),
  убитый — `victim`.
- Имена-заглушки в v1 (рандомные имена — v2).

Правила размещения (выполняются одновременно):
1. Каждый человек занимает ровно одну клетку; в одной клетке не более одного человека.
2. Человек не может стоять на клетке с **полным** объектом.
3. Все люди в **разных строках** и в **разных столбцах**.
4. **Комната убийства** (комната убитого): в ней ровно убитый и убийца, т.е. ровно
   2 человека и ровно 1 подозреваемый.
5. Для остальных комнат ограничений нет (пустые допустимы, если не запрещены подсказками).

Игрок не знает заранее, какая комната — комната убийства; это часть вывода.

## 4. Подсказки

Каталог конечен и перечислим. Все подсказки — **истинные утверждения о решении**
(ложных нет). Убитый **не упоминается** в подсказках классов A/B/C напрямую; счётчики
комнат (класс D) учитывают всех людей, включая убитого.

Обозначения: `P` — подозреваемый, `O` — тип объекта, `R_i` — комната, `k` — число.
`adj(a, b)` — клетки имеют общую сторону; клетка не соседствует сама с собой.

**Экзистенциальная семантика по типу** (типы могут повторяться):
- «на `O`» = клетка человека содержит *некоторый* экземпляр типа `O`;
- «рядом с `O`» = ∃ клетка `x` с экземпляром `O`: `adj(клетка(P), x)` **и** клетки `x` и `клетка(P)` находятся в одной комнате **и** клетка `P`
  сама не содержит экземпляр `O` (стоящий на объекте не «рядом» с ним — правило
  применяется к обеим клеткам кровати);
- «в комнате, где есть `O`» = комната человека содержит ≥ 1 экземпляр `O`;
- отрицания — универсальные («не на ковре» = человек не стоит ни на одном ковре).

### A. Человек–объект (на клетке) — только подозреваемые

| # | Семантика | Формулировка (RU) |
|---|---|---|
| A1 | клетка `P` содержит экземпляр `O` | «Подозреваемый_1 был на кровати» |
| A2 | не A1 | «Подозреваемый_1 был не на ковре» |
| A3 | «рядом с `O`» (определение выше) | «Подозреваемый_1 был рядом со шкафом» |
| A4 | не A3 | «Подозреваемый_1 был не рядом со шкафом» |

### B. Человек–объект (на комнате) — только подозреваемые

| # | Семантика | Формулировка |
|---|---|---|
| B1 | комната `P` содержит экземпляр `O` | «Подозреваемый_1 был в комнате, где есть стол» |
| B2 | не B1 | «Подозреваемый_1 был в комнате, где нет стола» |

### C. Человек–человек — только подозреваемые

| # | Семантика | Формулировка |
|---|---|---|
| C1s/n | `row(P1) > / < row(P2)`, столбец любой | «Подозреваемый_1 был южнее / севернее Подозреваемого_2» |
| C1e/w | `col(P1) > / < col(P2)`, строка любая | «…был восточнее / западнее…» |
| C2 | `room(P1) = room(P2)` | «Подозреваемый_1 и Подозреваемый_2 были в одной комнате» |
| C3 | не C2 | «Подозреваемый_1 и Подозреваемый_2 были в разных комнатах» |

### D. Комнаты — считаются все люди (включая убитого)

| # | Семантика | Формулировка |
|---|---|---|
| D1 | `\|people(R_i)\| op k`, `op ∈ {=, ≠, >, ≥, <, ≤}` | «В комнате_3 было ровно 2 человека» / «более 1 человека» / «не менее 2 человек» / «менее 2 человек» / «не более 2 человек» / «не 2 человека» |
| D2 | ∀ комнат `\|people\| ≥ 1` (глобальная, без параметров) | «Пустых комнат не было» |

Русские формулировки D1 — с правильными склонениями числительных
(функция плюрализации: 1 человек, 2–4 человека, 5+ человек, 11–14 человек).

### Формат данных пазла

Пазл — структурированный JSON (бэкенд → фронтенд; решения в нём нет):

```json
{
  "width": 7, "height": 7,
  "rooms":   [{ "id": 1, "cells": [{ "r": 0, "c": 0 }] }],
  "objects": [{ "id": "obj_1", "type": "table", "cells": [{ "r": 2, "c": 3 }] }],
  "people":  [{ "id": "suspect_1", "name": "Подозреваемый_1", "portrait_seed": 1234567 },
              { "id": "victim",    "name": "Убитый",          "portrait_seed": 7654321 }],
  "clues":   [ /* см. ниже */ ]
}
```

- `people`: подозреваемые по порядку номеров, убитый последним; убитый определяется
  `id == "victim"`.
- `portrait_seed` — 32-битное случайное число из RNG генератора; фронтенд детерминированно
  строит из него портрет v1 (цвет: `hue = seed % 360`; инициал: «П{n}», у убитого — череп).

### Формат данных подсказки

```json
{
  "kind": "on" | "not_on" | "adjacent" | "not_adjacent"
        | "room_has_object" | "room_not_has_object"
        | "south" | "north" | "east" | "west"
        | "same_room" | "not_same_room" | "room_count" | "no_empty_rooms",
  "person": "suspect_1",      // id, только для A/B/C
  "person2": "suspect_2",     // только для C
  "object_type": "bed",       // только для A/B
  "room": 3,                  // только для D1
  "count": 2, "op": "eq"      // только для D1; op: eq|ne|gt|ge|lt|le
}
```

Русский текст рендерит фронтенд (единая функция `clueToText`), бэкенд отдаёт только
структуру.

### Решение и победа

- Подсказки + правила §3 имеют **ровно одно** размещение всех `N` людей
  (размещение = отображение `person_id → (r, c)`).
- Убийца — единственный подозреваемый в комнате убитого (следствие уникальности).
- **Победа** = все `N` людей (включая убитого) на верных клетках **и** верно указан
  убийца.
- Промежуточной обратной связи при расстановке нет; проверка — только по явному
  действию игрока.

## 5. Солвер

- Вход: пазл. Выход и сигнатуры:
  - `count_solutions(puzzle, limit=2) -> int` — подсчёт решений с ранним выходом;
  - `solutions(puzzle, limit) -> Iterator[dict[person_id, (r, c)]]` — перечисление.
- Реализация — чистый Python: домены «человек → допустимые клетки» (только клетки
  игрового поля, без полных объектов), backtracking с MRV, проверка биекции
  строк/столбцов на лету, предвычисленные mask-предикаты подсказок по клетке/комнате.
- Отсечение по комнате убийства: до размещения убитого не применяется; после размещения
  убитого ровно один из остальных людей может находиться в его комнате (остальные —
  вне); проверяется при поиске и на полных назначениях.
- Библиотеки разрешены: если профилирование покажет, что генерация не укладывается
  в лимиты — перенос домена на OR-tools CP-SAT. Базовая версия — без зависимостей.
- Производительность: `count_solutions` на 9×9, N=9 — < 100 мс (генератор делает
  сотни вызовов на пазл).

## 6. Генератор

Параметры сложности (объекты, комнаты и люди — случайные из промежутка):

| Сложность | Поле  | N   | Объектов (≈10–30% площади) | Комнат |
|-----------|-------|-----|----------------------------|--------|
| easy      | 6×6   | 4–5 | 6–10                       | 3–5    |
| medium    | 7×7   | 5–7 | 5–15                       | 5–10   |
| hard      | 8×8   | 6–8 | 7–19                       | 6–13   |
| expert    | 9×9   | 7–9 | 8–24                       | 7–16   |

(`Комнат` — число комнат **включая пустоты**; игровых комнат на поле = значение из
промежутка минус `x`, см. шаг 1.)

**Детерминированность**: весь пайплайн использует один экземпляр `random.Random(seed)`;
лимит попыток на шаг — 50; при исчерпании — новая внешняя попытка (тот же RNG, до 40
внешних попыток), т.е. **один seed всегда даёт один и тот же пазл**. Конкретный seed
может на законных основаниях исчерпать все попытки (см. §7 — поведение API).

Пайплайн:

1. **Комнаты**: сначала выбирается число исключаемых комнат `x ∈ {0,1}`, затем
   `R + x` — значение из промежутка таблицы (`R` — целевое число комнат на игровом
   поле, т.е. после исключения пустот),
   region-growing (BFS от семян в случайном порядке), размер комнаты **≥ 2**
   (одноклеточных нет), сверху не ограничен; полное покрытие прямоугольника.
2. **Пустоты**: исключить `x` случайных комнат (суммарно ≤ 30% площади
   прямоугольника). Валидация силуэта: в каждой строке и каждом столбце ≥ 1 клетки
   игрового поля; иначе откат (повтор шагов 1–2 с новыми бросками RNG).
3. **Объекты**: `k` экземпляров из промежутка; типы сэмплируются **с повторениями**
   из пула; клетки — случайные различные клетки игрового поля; кровать занимает
   случайную клетку + случайного ортогонального соседа в той же комнате; доля полных
   ~40%. Валидация: в каждой строке и каждом столбце ≥ 1 допустимой для человека
   клетки, всего допустимых ≥ N; иначе откат.
4. **Люди**: выбрать комнату убийства с ≥ 2 допустимыми клетками в разных строках
   и столбцах; разместить там убитого и убийцу; остальных — backtracking по правилам
   **1–4 §3** (в частности, никто из них не попадает в комнату убийства).
   Убитый ставится на «заблокированную» клетку: после размещения убитого и убийцы
   в комнате убийства не должно существовать другой допустимой для человека клетки,
   у которой одновременно свободны её строка и её столбец. Иначе полный набор
   подсказок в принципе не различает позиции убитого внутри его комнаты (убитый
   не упомянут в A/B/C, а D-счётчики зависят только от комнаты) — требуемая
   уникальность размещения недостижима, попытка отбрасывается.
5. **Подсказки**: перечислить **все** истинные подсказки каталога в следующих доменах:
   - A/B: каждый подозреваемый × каждый тип объекта, **присутствующий** на поле
     (по отсутствующим типам подсказки не строятся — они вакуумно истинны);
   - C1: все упорядоченные пары подозреваемых; C2/C3: все неупорядоченные пары;
   - D1: каждая комната × каждый `op` × `k ∈ {0..N}` (только истинные комбинации);
   - D2: глобальная, если истинна.
   Затем **жадное прореживание** в два прохода (тем же RNG): сначала перемешать
   и пропросить только направленные C1, затем — все остальные; подсказка
   удаляется, если после удаления `count_solutions` остаётся `1`. C1
   прореживается первым: все направленные, избыточные в полном наборе,
   удаляются до того, как тронуты остальные виды, — в итоговых наборах их
   мало, а уникальность сохраняется. Итог —
   локально-минимальный набор (никакую подсказку нельзя убрать, сохранив
   уникальность), подтверждённый солвером.
6. Метаданные: seed, параметры, число подсказок, время генерации.

Требование: генерация expert — < 3 с в среднем (иначе — OR-tools, §5).

## 7. Игра (UI и контракт проверки)

### UI

- Слева поле: стены — толстые линии, комнаты — фоновые оттенки, пустоты не
  отрисовываются, объекты — иконки; полные объекты перекрывают клетку; кровать
  рисуется на обеих клетках; соседние однотипные сливаемые объекты одной комнаты
  сливаются визуально (§2).
- Справа: список подсказок, палитра подозреваемых (drag-источники) и убитый,
  кнопка «Обвинить».
- Номер комнаты отображается бейджем с числом в угловой клетке комнаты (§1) —
  на него ссылаются подсказки D1.
- Справа также: выбор сложности (easy/medium/hard/expert) и кнопка «Новая игра».
- **Drag & drop** портрета на клетку; клик по размещённому — вернуть в палитру;
  **клик по клетке без человека — красный крестик** («здесь никого»), повторный клик
  снимает.
- Бросок портрета игнорируется (без эффектов) на: клетке с уже размещённым человеком,
  клетке с полным объектом, пустоте.
- Убитый визуально отличается (чёрная лента/череп). Портреты v1 — цвет + инициал из
  `portrait_seed` (§4).
- «Обвинить» доступно при всех размещённых + введённом имени подозреваемого (input
  с подсказкой-списком имён).
- Русский язык UI.

### API

- `GET /api/puzzle?difficulty={easy|medium|hard|expert}[&seed=N]` →
  `{"puzzle": {…см. §4…}, "token": "…"}`. Без `seed` пазл генерируется из случайного
  seed; с `seed` — детерминированно (§6). При неудаче генерации (`GenerationError`):
  для запроса **без** `seed` сервер молча повторяет попытку с новыми случайными seed
  (до `GENERATION_RETRIES = 5`), и лишь после исчерпания отвечает
  `503 {"error": "…"}`; для запроса **с явным** `seed` — ровно одна попытка, seed не
  подменяется (контракт «один seed ⇒ один пазл»), неудача → `503 {"error": "…"}`.
- `POST /api/check` — контракт ниже.
- Статика фронтенда отдаётся тем же сервером с корня `/`.
- Ключ токенов — `MURDOKU_SECRET` (обязателен); если не задан: при `MURDOKU_DEV=1` —
  случайный ключ процесса с предупреждением (токены недействительны после рестарта),
  иначе ошибка старта сервера.

### Проверка (контракт)

- Решение клиенту в открытом виде не отдаётся: сервер выдаёт пазл + **токен** —
  payload (решение, сложность, game_id), зашифрованный аутентифицированным шифрованием
  (AES-GCM/Fernet, ключ из `env MURDOKU_SECRET`). Клиент не может прочитать решение;
  сервер ничего не хранит (stateless).
- Запрос: `POST /api/check` `{token, placements: [{person_id, r, c}] (все N людей),
  accusation: person_id}`.
  Обвинение сервер сравнивает **по id** точно; фронтенд превращает введённый текст
  в id (сопоставление имени после trim без учёта регистра; если имя не распознано —
  запрос не отправляется).
- Ответ:
  - победа: `{won: true}`;
  - есть неверно размещённые: `{won: false, misplaced_person_id}` — **ровно один**
    id: первый неверный в порядке «suspect_1…suspect_{N−1}, victim» (подозреваемые
    по номерам, убитый последним), без перечня остальных;
  - все размещены верно, но обвинение неверно: `{won: false, correct_accusation: false}`.
- Поведение после ответа:
  - `{won: true}` — экран раскрытия (убийца + верная расстановка, которую сервер
    возвращает в этом ответе полем `solution`), кнопка «Новая игра»;
  - провал — игрок остаётся на поле, может переставлять людей и обвинять снова
    (число попыток не ограничено); при `misplaced_person_id` этот человек
    подсвечивается.

## 8. Реализация

- Бэкенд: Python 3.12+ (в окружении 3.14); ядро (модель, солвер, генератор) — только
  стандартная библиотека; сервер — Starlette + uvicorn; токены — `cryptography`
  (Fernet). Тесты — pytest.
- Фронтенд: ванильный JS (ES-модули, без сборки), отдаётся бэкендом как статика;
  чистая логика (clueToText, портреты) покрывается `node --test`.
- Компоновка: `backend/` (пакет `murdoku`, `tests/`, `scripts/`), `frontend/`
  (index.html, styles.css, js/). Технические контракты модулей и API —
  в `ARCHITECTURE.md`; ход работ — в `PROGRESS.md`.
